# 관리자 신고 조회 — 설계안 (design doc)

**작성: 2026-08-03 · 상태: 🟡 검토 요망 (brainstorming 산출물)**
**선행: `2026-08-02-report-suggestion-design.md` §7 후속 항목 1**

---

## 1. 목표 · 범위

관리자가 접수된 신고·건의를 읽고 처리 여부를 표시할 수 있게 한다.

**현재 상태:** 유저는 `POST /reports`로 신고·건의를 제출할 수 있지만 **읽을 수단이 전혀 없다.** 조회 API도, 관리자 화면도 없다. 기능이 반만 열려 있는 상태이며 `CLAUDE.md` 미결 항목에 등재돼 있다.

**이 설계가 만드는 변경:**
1. `Report.handled` 컬럼 추가 (+ 마이그레이션)
2. `GET /admin/reports`, `POST /admin/reports/{id}/handle`
3. `Admin` 페이지를 탭 구조로 재편 + `ReportTab` 신규
4. `/report` 화면에 작성자 정보 전달 고지 1줄

**범위 밖:**
- ⛔ 매칭 알고리즘
- 제재 조치(경고·정지) 기능 — 제재 정책이 팀 미결
- 신고 삭제 API, 처리 되돌리기, 페이징, 감사 추적(`handled_at`/`handled_by`)

## 3. 데이터 모델

`Report`에 컬럼 1개 추가:

```
handled   Boolean, nullable=False, default False
```

`handled_at`(처리 시각)·`handled_by`(처리한 관리자)는 넣지 않는다. 현재 요구는 "처리했는지 여부"뿐이고, 감사 추적 요구가 생기면 그때 추가한다.

**마이그레이션:** `op.add_column("reports", sa.Column("handled", sa.Boolean(), nullable=False, server_default="false"))`. `downgrade`는 `drop_column` 하나.

`server_default="false"`는 여기서 안전하다. `User.gender`에서 문제가 됐던 것은 기본값의 존재가 아니라 **기본값이 기존 행에 대해 거짓이었다는 점**이다(여성 유저가 `male`이 됨). `handled=false`는 기존 신고에 대해 참이므로 백필 숙제가 생기지 않는다.

착수 시 `reports` 행 수를 확인한다. 새 enum 타입을 만들지 않으므로 `add_column`이 `CREATE TYPE`을 발행하지 않는 PostgreSQL 함정(`33aa8ba5f23f`, `f791f9b09268`에서 겪은 것)은 이번에 해당하지 않는다.

## 4. API 계약

엔드포인트 2개. 둘 다 `require_admin`(`app/core/deps.py`), 기존 `/admin/verifications` 패턴을 따른다.

### `GET /admin/reports`

| 쿼리 | 기본값 | 동작 |
|---|---|---|
| `include_handled` | `false` | `false` = 미처리만, `true` = 전체 |

정렬: `created_at` 내림차순.

**페이징 없음.** 운영 전이라 데이터가 0건이고, 페이징은 총 건수·커서 등 추가 결정을 끌고 온다. 목록이 실제로 길어지면 그때 도입한다.

**응답 `AdminReportOut`**

```
id, type, target_name, target_university, reason, created_at, handled,
reporter_name, reporter_university
```

`reporter_name`·`reporter_university`는 `users` 조인으로 채운다. `reporter_id`(내부 PK)는 응답에 넣지 않는다 — 화면에서 쓸 일이 없고, 유출된 id는 다른 API를 찌르는 재료가 된다.

### `POST /admin/reports/{report_id}/handle`

`handled = True`로 표시하고 갱신된 `AdminReportOut`을 반환한다.

- **멱등**: 이미 `handled=True`여도 200. 더블클릭·재시도에서 에러를 띄우는 이득이 없다.
- **되돌리기 없음**: 실수로 눌렀을 때 복구 수단이 없다는 트레이드오프를 감수한다. 필요해지면 `unhandle`을 추가하되, 그때는 "왜 되돌렸는지" 기록 요구가 함께 온다.
- 없는 id → 404 `"존재하지 않는 신고입니다"`

**신고 삭제 API는 만들지 않는다.** 신고 기록은 분쟁 근거이므로 삭제가 기본 동작이 되면 안 된다.

## 5. 프론트엔드

**파일 재구성** — `Game.tsx:8-32`의 탭 구조를 그대로 따른다.

| 파일 | 변화 |
|---|---|
| `Admin.tsx` | 탭 컨테이너로 축소. 탭 버튼 2개 + 분기 |
| `VerificationTab.tsx` | 신규. 현 `Admin.tsx`의 `Card` + 목록 로직을 **그대로 이동**. 로직 변경 없음 |
| `ReportTab.tsx` | 신규 |
| `Admin.module.css` | 탭 스타일 추가(`Game.module.css`의 `.tabs`/`.tab`/`.tabActive` 참고) |
| `Admin.test.tsx` | 기존 내용을 `VerificationTab.test.tsx`로 이동. `Admin.test.tsx`는 탭 전환만 검사 |

학생증 심사 코드는 **옮기기만 하고 고치지 않는다.** 이동과 변경이 한 diff에 섞이면 리뷰가 둘을 구분할 수 없다.

**`ReportTab` 화면**

```
[ ] 처리된 항목도 보기          ← 기본 해제

┌─────────────────────────────┐
│ [신고]  대상: 홍길동 · 연세대   │
│ 신고자: 김철수 · 서울대         │
│ 2026-08-03 14:30             │
│ ───────────────────────────  │
│ 본문 …                        │
│               [처리 완료]      │
└─────────────────────────────┘
┌─────────────────────────────┐
│ [건의]                        │  ← 대상 줄 없음
│ 작성자: 이영희 · 고려대         │
└─────────────────────────────┘
```

- 유형 배지로 신고/건의 구분. 건의는 대상 줄을 **렌더링하지 않는다**(`/report` 폼에서 입력칸을 언마운트한 것과 같은 원칙).
- "처리 완료" 클릭 → `POST .../handle` 후 목록에서 제거. `Admin.tsx:93-95`의 `removeItem` 패턴과 동일.
- "처리된 항목도 보기"가 켜져 있으면 제거하지 않고 흐리게 표시하고 버튼을 숨긴다.
- 로딩·에러 문구는 기존 관리자 화면과 통일한다. 빈 목록 문구는 `"신고·건의 없음"`.

**`/report` 고지 문구:** 유형 선택 아래에 `"작성 내용과 작성자 정보는 관리자에게 전달됩니다"`. Q3에서 신고자 신원을 관리자에게 표시하기로 했으므로 유저에게 고지한다.

## 6. 신고자 신원을 표시하는 이유

관리자에게 신고자 이름·학교를 보여준다.

- 사실관계 확인 문의가 가능하다.
- **허위·보복 신고를 탐지할 수 있다** — 같은 사람이 같은 대상을 반복 신고하는 패턴은 신고자를 봐야 보인다.
- 관리자는 이미 학생증 원본을 열람하는 권한이므로 신원 노출 수위가 새로 올라가지 않는다.

오작교의 "지목자 익명"은 **유저끼리** 가리는 규칙이지 관리자에게까지 가리는 것이 아니다. 신고는 성격상 관리자의 사실판단이 필요하다.

**감수하는 트레이드오프:** 신고자가 "내가 신고한 사실이 관리자에게 드러난다"는 부담을 진다. §5의 고지 문구로 최소한 예측 가능하게 만든다. 내부 id만 노출하는 절충안은 DB를 조회하면 신원이 나오므로 실질 보호가 아니라 표시상의 가림에 그친다.
