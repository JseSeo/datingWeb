# 매칭 엔진 성능 — networkx → scipy 교체 설계

> 이 문서는 **결정 근거와 실측치**를 남긴다.
> 확정된 내용은 `2026-08-21-matching-algorithm-design.md`의 §5.1·§5.2·§12에 반영한다.
> 스펙은 하나다 — 충돌하면 그쪽이 진실이다.

## 1. 문제

`optimal_pairs`(점수표를 받아 총점 최대인 짝 목록을 내는 함수)가 쓰는
`nx.max_weight_matching`(networkx의 최대 가중치 매칭 함수)은 순수 Python 구현이라
풀이 커지면 급격히 느려진다. 인원이 2배면 시간은 약 8배다.

| 풀 | `nx.max_weight_matching` |
|---|---|
| 500명 | 44s (스펙 §5.1 실측) |
| 1,000명 | 170~185s (스펙 §5.1 실측) |

리버스 프록시·PaaS 기본 타임아웃은 30~60초다. **문제는 1,000명이 아니라 500명대에서 이미 시작된다.**
관리자 화면엔 실패가 뜨는데 백엔드는 계속 돌아 라운드를 `done`으로 만든다.

## 2. 실측 (2026-08-30, 이 설계를 위해 측정)

동일 머신, 남녀 각 절반, 간선 20% 제거(절대질문·과거이력 모사).

| 풀 | 현재 networkx | scipy 교체안 | 배수 |
|---|---|---|---|
| 200명 | 0.83s | 0.004s | 190× |
| 500명 | 14.3s | 0.034s | 420× |
| 1,000명 | (스펙 실측 170~185s) | 0.14s | — |

교체 후 병목은 매칭이 아니라 **점수 계산**(1,000명 기준 약 8s)으로 넘어간다.

## 3. 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 엔진 | `scipy.optimize.linear_sum_assignment` | 위 실측 |
| 목적함수 | **유지** — 총점 최대, 필요하면 사람을 남긴다 | 스펙 §4·§5.2 설계를 손대지 않는다 |
| 목적함수 유지 방법 | 패딩 행렬(§5) | 헝가리안은 기본이 전원 강제 매칭이라 그대로 쓰면 목적함수가 바뀐다 |
| tie-break 기준 | `raw id 간격` → **`id 순번 간격`** | float64 정확 정수 한계(§6). 불가피한 변경 |
| 정밀도 초과 시 | **예외를 던진다** | 조용히 틀린 짝을 내는 것이 가장 나쁜 실패 |
| `optimal_pairs` 시그니처 | `male_ids`(남성 id 집합) 인자 추가 | 행렬을 만들려면 양쪽 구분이 필요한데 점수표에 그 정보가 없다 |
| networkx 의존성 | 제거 | 교체 후 `pairing.py` 외 사용처가 없다 |

## 4. 시그니처 변경

```python
def optimal_pairs(scores, male_ids: set[int]) -> list[tuple[int, int]]
```

`scores`(점수표)의 키는 `pair_key`(두 id를 작은 것 먼저로 정규화하는 함수)를 거쳐
`(작은 id, 큰 id)`로 통일돼 있다. 즉 **어느 쪽이 남성인지가 이미 지워져 있다.**
networkx는 일반 그래프 알고리즘이라 이 정보가 필요 없었지만, 행렬은 행과 열을 나눠야 하므로 필요하다.

호출부 비용은 0이다. `matching.py`에 `male_ids`가 이미 있다:

```python
male_ids = {user.id for user in men}          # 저장 축 고정에 쓰려고 이미 만들어 둔 집합
pairs = guaranteed + optimal_pairs(remaining, male_ids)
```

**검토 후 버린 대안**

- *그래프에서 양분을 추론* — 호출부가 아는 것을 15줄 들여 다시 계산한다. 간선이 하나도 없는
  사람은 판정 근거가 없고, 동성 페어가 버그로 섞여도 조용히 통과한다
- *`scores` 키 규약을 `(남, 여)`로 변경* — 그 규약을 `excluded`·`red`·`ojakgyo_counts`·
  `base`·`adjusted` 다섯 곳이 공유한다. 스펙 §6.1이 의도한 두 규약의 분리를 깬다

## 5. 패딩 행렬

헝가리안은 작은 쪽 전원을 강제로 짝지운다. 현재 목적함수는 **총점이 더 크면 사람을 남긴다**
(예: A–B 90점 하나가 A–C 1점 + D–B 1점보다 낫다). 그대로 쓰면 이 성질이 사라진다.

`(n+m) × (n+m)` 정사각 행렬로 미매칭을 명시적 선택지로 만들면 목적함수가 보존된다.

```
              여 0..m        남의 미매칭 슬롯
           ┌────────────┬──────────────────┐
 남 0..n   │  실제 점수   │ 대각 0, 나머지 -BIG │
           ├────────────┼──────────────────┤
 여의      │ 대각 0      │        0         │
 미매칭    │ 나머지 -BIG  │                  │
 슬롯      └────────────┴──────────────────┘
```

- 미매칭이 항상 0점으로 가능하므로, 금지 페어(음수)는 절대 선택되지 않는다
- 남녀 인원이 달라도 남는 쪽은 자기 미매칭 슬롯으로 흘러간다
- 결과에서 `행 < n` **그리고** `열 < m`인 칸만 실제 짝으로 취한다.
  그 칸이 `-BIG`이 아님을 단언한다 — 금지 페어가 새어 나오면 즉시 터뜨린다
- `-BIG`은 `-1e18`. 실제 가중치 최댓값(2⁵³ 미만)보다 충분히 작아 절대 선택되지 않는다

메모리는 `풀²  × 8B` — 1,000명 8MB / 2,000명 32MB / 4,000명 128MB.

### 동치성 검증 (측정)

| 케이스 | 결과 |
|---|---|
| 랜덤 60·80·120·150·200명 | 짝 **완전 일치** |
| 손수 만든 반례 (90점 하나 vs 1점 둘) | 둘 다 90점 한 쌍만 선택, 2명 미매칭 |
| 희소 그래프 (미매칭 8~18명) | 짝 완전 일치 |
| 남녀 불일치 (30/20, 15/45, 1/9) | 짝 완전 일치 |

## 6. 정밀도 — tie-break 기준 변경

float64는 정수를 **2⁵³ ≈ 9.0e15까지만 정확히** 담는다. 그 위에서는 `2**53 + 1 == 2**53`이다.

`pairing.py`의 tie-break는 정수 연산이 정확하다는 전제 위에 있다:

```
weight = base × big − tie
```

`tie`(동점 판정 항)는 `big`(점수를 tie보다 우선하게 만드는 배수)에 비해 아주 작다.
`base × big`이 2⁵³을 넘으면 **`− tie`가 반올림에 먹혀 사라지고**, 동점 페어들이 전부 같은
가중치가 되어 tie-break가 무력화된다. 스펙 §5.2의 "같은 입력은 항상 같은 결과"가 조용히 깨진다.

Python 정수는 무한 정밀도라 networkx 경로에는 이 문제가 없었다. **scipy로 옮기는 행위가 만드는 위험이다.**

### 원인과 해결

현재 `tie`는 raw user id로 계산된다 — `tie_bound = (최대 id + 1)²`.
실제 user id가 50,000이면 풀 1,000명에서 가중치가 **1.25e17**로 한계를 넘는다.
**현재 인코딩 그대로는 scipy에 넣을 수 없다.**

id를 등장 순서 랭크(0..N-1)로 압축해 `tie = (순번 차이)²`로 바꾼다.
`tie_bound`(tie 항의 상한)와 `big`도 raw id가 아니라 인원 수 N으로 계산된다.

```python
ids  = sorted(scores에 등장하는 모든 id)     # N개
rank = {id: 순번}                            # 0..N-1

tie_bound = (N + 1) ** 2                     # 이전: (최대 id + 1)²
big       = tie_bound * (N // 2 + 1)         # 한 매칭의 tie 총합보다 크다
weight    = base * big - (rank_b - rank_a) ** 2
```

`big`이 tie 총합보다 크다는 성질은 그대로다 — 간선 수가 `N//2` 이하이고 각 tie가
`tie_bound` 미만이므로, 점수부가 항상 tie를 이긴다.

| 풀 N | 최대 가중치 | 2⁵³ 대비 |
|---|---|---|
| 1,000명 | 5.0e13 | 0.6% |
| 2,000명 | 4.0e14 | 4% |
| 4,000명 | 3.2e15 | 36% |
| 약 5,600명 | 9.0e15 | 한계 |

### 대가 — 동점 조합 선택이 달라진다 (측정)

id 간격 대신 순번만 보므로, 동점일 때 고르는 조합이 지금과 달라질 수 있다.
동점을 대량 발생시킨 40케이스(희소 id):

| 항목 | 결과 |
|---|---|
| 총점 | **다름 0건** |
| 매칭 쌍 수 | **다름 0건** |
| 짝 구성 | 다름 27건 |
| 같은 입력 5회 반복 | 결과 동일 (결정론 유지) |

즉 **더 나쁜 매칭이 아니라 동점 조합 중 다른 하나**다. 스펙 §5.2의 핵심 요구인 재현성은 유지되고,
"작은 id 우선"이 "작은 순번 우선"으로 바뀐다 (순서는 보존, 간격만 무시).

id가 촘촘한 입력(1..N)에서는 앞선 모든 케이스가 일치했다. 실제 DB는 autoincrement라
탈퇴가 쌓이기 전까지는 차이가 드물 것이다.

### 가드

```python
if max_base * big > 2**53:
    raise ValueError(...)
```

`max_base`(점수표 중 가장 큰 `base` 값)는 점수 상한을 코드에 박지 않고 입력에서 뽑는다.
실패는 `run_matching`(라운드 실행 진입점)의 `except Exception`이 받아 전부 롤백하고
라운드를 `pending`으로 되돌리므로, 관리자는 에러를 보고 재실행할 수 있다.

*버린 대안*: 문서화만 하기(조용한 파손이 그대로 남음), 자동 축소(결과 성질이 조용히 바뀜).

## 7. 범위

| 파일 | 변경 |
|---|---|
| `services/pairing.py` | networkx → scipy. 랭크 압축 + 패딩 행렬 + 정밀도 가드 |
| `services/matching.py` | `optimal_pairs` 호출 1줄, `eligible_users`에 `joinedload(User.survey)` 1줄 |
| `pyproject.toml` | `networkx` 제거, `scipy` 추가 |
| `tests/test_pairing.py` | 기존 유지 + 신규 6개 |
| 매칭 알고리즘 스펙 | §5.1·§5.2·§12 반영 |

API·프론트·DB 스키마는 변경 없다. `optimal_pairs`의 반환 형태가 그대로라 파급이 여기서 멈춘다.

`joinedload(User.survey)`는 후속 티켓 M1이다. `eligible_users`(매칭 대상자 조회 함수)가
유저마다 설문을 따로 읽어 1,000명이면 쿼리가 1,001번 나간다. 같은 파일을 여는 김에 함께 처리한다.

## 8. 테스트

**기존 테스트가 1차 검증이다.** `test_pairing.py`·`test_matching.py`의 30개가 그대로 통과해야 한다.
`conftest`가 테스트마다 DB를 재생성해 id가 1부터 시작하므로 촘촘한 id다 — 차이가 없을 것으로 예상하되 실제로 확인한다.

신규 6개:

| 테스트 | 무엇을 잡나 |
|---|---|
| 금지 페어는 절대 선택되지 않는다 | `-BIG` 칸이 결과에 새어 들어오는 버그 |
| 총점을 위해 사람을 남긴다 (90 vs 1+1) | 패딩이 빠져 전원 강제 매칭으로 퇴화하는 것 |
| 남녀 인원이 달라도 동작 | 직사각 처리 |
| 같은 입력 반복 시 같은 결과 | 결정론 |
| 크고 희소한 id에서 동작 | 랭크 압축 누락 |
| 정밀도 초과 시 예외 | 가드 제거 |

정밀도 테스트는 노드 2개에 거대한 점수를 주어 `max_base × big` 곱을 넘긴다 — 5,600명을 만들 필요가 없다.

## 9. 한계

- 약 5,600명에서 정밀도 한계에 도달한다. 그때는 점수 스케일 축소가 필요하다
- 교체 후 병목은 점수 계산(1,000명 ~8s, O(n²))으로 옮겨간다. 2,000명대에서 다시 검토할 항목이다
- scipy·numpy가 새 의존성으로 추가된다 (배포 이미지 증가)
