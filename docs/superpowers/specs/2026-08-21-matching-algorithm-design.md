# 매칭 알고리즘 설계

> 작성: 2026-08-21
> 상위 스펙: `2026-05-23-datedrop-korea-design.md` (§5 매칭 시스템)
> 이 문서가 §5.2 "보류"를 대체한다.

---

## 1. 개요

주 1회 라운드마다 남성 1명 ↔ 여성 1명을 짝짓는다. 가치관 설문 응답으로 궁합 점수를 계산하고,
절대질문을 하드필터로 적용한 뒤, 전체 만족도 합이 최대가 되는 조합을 찾는다.

**핵심 결정 요약**

| 항목 | 결정 |
|---|---|
| 질문 카탈로그 위치 | 백엔드가 정본. 프론트는 API로 받아 렌더 |
| 페어 점수 합산 | `min(A→B, B→A)` — 한쪽만 만족하는 짝 방지 |
| 짝짓기 방식 | 전체 최적 (max weight matching) |
| 최소 점수 컷 | 없음 — 절대질문만 통과하면 매칭 |
| 이월 처리 | 미매칭자에게 점수 보너스 가산 (상한 있음) |
| 대학 가중치 | 단일 대학 + 대학쌍 두 종류, 관리자 화면에서 설정 |
| 절대질문 vs 게임 보장 | 절대질문이 이긴다 |
| 재매칭 | 영구 금지 |
| 게임 대상 식별 | 이름+학교+학번, 유일 특정될 때만 적용 |
| 매칭 자격 | active + 일시정지 OFF + 설문 저장 이력 있음 |
| 문항 가중치 | 카테고리별 4단계 |
| 조정값 위치 | 대학 가중치만 DB, 나머지는 코드 상수 |
| 결과 전달 | 인앱 화면 (알림톡은 사업자등록 후 병행) |
| 실행 방식 | 관리자 버튼 수동 |

## 2. 파이프라인

```
1. 풀 구성      active + matching_paused=false + 설문 저장 이력  →  남자풀 / 여자풀
2. 후보 생성    남 × 여 전체 조합
3. 하드필터     절대질문 위반 제거  +  과거 매칭 이력 제거
4. 기본 점수    설문 궁합 (양방향 min)                              0~100
5. 보정         + 이월 보너스  + 대학 가중치  + 게임 보너스
6. 보장 확정    붉은실 상호 / 오작교 3인 → 먼저 짝 확정 (3번 통과분만)
7. 전체 최적    남은 인원으로 점수 합 최대 조합 계산
8. 저장         Match 행 생성 + missed_rounds 갱신
```

전체가 **한 트랜잭션**이다. 중간 실패 시 전부 롤백되고 라운드는 `pending`으로 돌아간다.
절반만 매칭된 상태는 생기지 않는다.

### 2.1 모듈 경계

| 파일 | 책임 | 의존 |
|---|---|---|
| `app/survey/catalog.py` | 45문항 정의 (질문·선택지·짝 관계·카테고리) | 없음 |
| `app/services/scoring.py` | 문항 만족도 → 방향 점수 → 페어 점수 | catalog만. DB 모름 |
| `app/services/pairing.py` | 점수표 → 최적 조합 | 숫자만. 설문·유저 모름 |
| `app/services/matching.py` | 위 8단계 오케스트레이션 | 전부 |
| `app/api/matching.py` | HTTP 껍데기 | `matching.py` 호출만 |

`scoring.py`·`pairing.py`가 DB를 모르는 것이 설계의 핵심이다. 순수 함수라 테스트가 쉽고,
나중에 실행 트리거를 스케줄러로 바꿔도 이 두 파일은 손대지 않는다.

**서비스 계층 분리 규칙**: 매칭 로직은 엔드포인트 안에 두지 않는다.

```python
# app/services/matching.py  ← 진짜 로직 (HTTP 모름)
def run_matching(db, round_id) -> MatchingResult: ...

# app/api/matching.py  ← 얇은 껍데기
@admin_router.post("/{round_id}/run")
def run_match(round_id, db, _=Depends(require_admin)):
    return run_matching(db, round_id)
```

추후 스케줄러 전환 시 `run_matching()`을 그대로 호출하면 된다.

## 3. 점수 계산

### 3.1 문항 만족도

각 `_pref` 문항마다 "상대의 `_self` 답이 내 선호를 얼마나 만족하나"를 `0.0 ~ 1.0`으로 계산한다.

**계산에서 제외되는 경우** (분자·분모 양쪽에서 빠짐):
- `_pref` 값이 해당 문항의 `noPrefId`("상관없음")
- 다중선택 문항에서 선택 목록에 `noPrefId`가 포함된 경우 (다른 값과 함께 골랐어도 "상관없음"으로 간주)
- `_pref` 또는 짝이 되는 `_self`가 미응답

`grooming_self`(남성 외모관리)는 짝이 되는 `_pref` 문항이 없다 → 매칭에 쓰지 않는다. 프로필 정보로만 남는다.

### 3.3 거주지 규칙

`residence_pref`("차로 N시간 이내")를 판정하려면 시·도 간 이동시간이 필요하다.
실제 도로 시간표 대신 **인접 그래프 홉 수**로 근사한다.

| 홉 수 | 간주 이동시간 |
|---|---|
| 0 (같은 시·도) | 1시간 |
| 1 (인접) | 2시간 |
| 2 | 3시간 |
| 3 이상 / 연결 없음 | 3시간 초과 |

| pref | 통과 조건 |
|---|---|
| `h1` (1시간↓) | 0홉→1.0, 1홉→0.5, 2홉↑→0.0 |
| `h2` (2시간↓) | 0~1홉→1.0, 2홉→0.5, 3홉↑→0.0 |
| `h3` (3시간↓) | 0~2홉→1.0, 3홉↑→0.0 |

**인접 시·도 목록** (무방향)

```
서울 – 인천, 경기
인천 – 서울, 경기
경기 – 서울, 인천, 강원, 충북, 충남
강원 – 경기, 충북, 경북
충북 – 경기, 강원, 충남, 세종, 대전, 경북, 전북
충남 – 경기, 충북, 세종, 대전, 전북
세종 – 충북, 충남, 대전
대전 – 충북, 충남, 세종
전북 – 충남, 충북, 전남, 경남, 경북
전남 – 전북, 광주, 경남
광주 – 전남
경북 – 강원, 충북, 전북, 경남, 대구, 울산
대구 – 경북
경남 – 전북, 전남, 경북, 부산, 울산
부산 – 경남, 울산
울산 – 경남, 경북, 부산
제주 – (없음)
```

제주는 육로 연결이 없다 → 제주끼리는 0홉(1시간), 그 외 모든 지역과는 "연결 없음"으로 처리한다.

이 근사는 실제 도로 시간보다 거칠지만 "서울↔부산은 멀다" 수준은 정확히 잡는다.
정밀화가 필요해지면 이 함수 하나만 교체하면 된다.

### 3.4 카테고리 가중치

문항별 개별 가중치는 두지 않는다. 카테고리 단위로만 무게를 다르게 한다.

| 카테고리 | 가중치 |
|---|---|
| 가치관·신념 | 1.5 |
| 관계·감정 | 1.3 |
| 경제·생활·건강 | 1.0 |
| 외모·스타일 | 0.8 |

코드 상수로 둔다. 운영 데이터가 쌓이면 조정한다.

### 3.5 점수 합산

**한쪽 방향 점수**

```
A→B = Σ(만족도 × 카테고리 가중치) / Σ(카테고리 가중치) × 100
```

제외 문항(상관없음·미응답)은 분자·분모 양쪽에서 빠진다.
따라서 설문을 일부만 채운 사람도 **답한 문항 비율로 환산**되어 불이익 없이 0~100 범위에 들어온다.

⚠️ **분모가 0인 경우** — 설문 행은 있으나 비교 가능한 문항이 하나도 없을 때
(예: 저장만 누르고 아무것도 안 채움, 또는 모든 `_pref`를 "상관없음"으로 답함).
이때 해당 방향 점수는 **0점**으로 처리한다. 0으로 나누지 않는다.
최소 점수 컷이 없으므로 이 유저도 매칭 대상에는 남는다.

**페어 점수**

```
score(A, B) = min(A→B, B→A)
```

한쪽만 만족하는 짝을 걸러내기 위함이다.

### 3.6 절대질문 하드필터

유저가 절대질문으로 지정한 문항은 상대가 **반드시** 만족해야 한다. 어기면 그 페어는 후보에서 제거된다.
양쪽 각각 최대 2개 (프론트에서 이미 강제).

| 문항 유형 | 통과 조건 |
|---|---|
| 일반 문항 | 만족도 **1.0** |
| 척도형 (`contact_freq` / `date_freq` / `alone_time` / `affection`) | 만족도 **0.75 이상** (차이 1칸 이내) |

척도형만 완화하는 이유: 척도는 1~5의 연속값이라 정확히 일치하는 사람만 통과시키면 후보가 거의 남지 않는다.
문신 유무 같은 이산 문항은 그런 문제가 없어 1.0을 유지한다.

**미응답으로 판정 불가한 경우 → 통과 처리.** 설문을 일부만 채워도 매칭 풀에 넣기로 했으므로,
판정 불가를 탈락 사유로 쓰면 그 결정과 충돌한다.

## 4. 보정

### 4.1 이월 보너스

`User.missed_rounds`(정수) 컬럼을 추가한다. 매칭 실행 후 **매칭된 사람은 0으로 리셋, 안 된 사람은 +1**.

갱신 대상은 **그 라운드 풀에 포함된 유저만**이다. 일시정지 중이거나 아직 승인 안 된 유저는
풀에 없으므로 `missed_rounds`가 오르지 않는다 — 참여하지 않은 라운드로 우선순위를 쌓는 일은 없다.

```
이월 보너스 = min(missed_rounds × 15, 45)
```

**상한이 필수적이다.** 상한이 없으면 10라운드 대기자가 +150점을 받아 원점수(최대 100점)를 압도한다.
그러면 알고리즘이 궁합을 무시하고 대기자끼리 묶어버려 최악 궁합 매칭이 양산되고, 그 유저들이 이탈해
문제가 더 나빠진다. 45점은 "많이 밀리지만 궁합을 뒤집지는 못하는" 수준이다.

보너스는 그 사람이 끼는 **모든 페어**의 점수에 더해진다. 전체 최적 계산이 자연스럽게 그 사람을
포함시키는 방향으로 기운다 — 별도 예외 코드가 필요 없다.

### 4.2 대학 가중치

테이블 하나로 단일 대학·대학쌍 둘 다 처리한다.

```
MatchingUniversityWeight
  id
  university_a   (필수)
  university_b   (필수, 빈 문자열이면 단일 대학 보너스)
  bonus          (정수, 음수 허용 = 페널티)
  active         (bool)
  note           (관리자 메모)
  unique(university_a, university_b)   -- 쌍은 사전순 정규화 후 저장
```

⚠️ `university_b`를 nullable로 두면 안 된다. SQLite·PostgreSQL 모두 **유니크 인덱스에서 NULL을 서로 다른 값으로
취급**하므로, `(A대, NULL)` 행이 여러 개 들어가도 DB가 막지 못한다. 같은 대학에 보너스 규칙이 중복 등록되면
합산되어 의도치 않게 큰 값이 된다. 단일 규칙은 `university_b = ''`(빈 문자열)로 저장해 유니크가 정상 동작하게 한다.

남성 대학 X, 여성 대학 Y인 페어에 대해:

| 규칙 종류 | 조건 | 결과 |
|---|---|---|
| 단일 | `university_a = X`, `university_b = ''` | +bonus |
| 단일 | `university_a = Y`, `university_b = ''` | +bonus |
| 쌍 | `{a, b} = {X, Y}` (순서 무관) | +bonus |

여러 규칙이 겹치면 **합산**하되, 총합은 **±50점**으로 제한한다.
관리자가 실수로 큰 값을 넣어도 매칭 전체가 망가지지 않게 하는 안전장치다.

`active=false`인 규칙은 무시한다 (이벤트 종료 시 삭제 대신 끄기).

대학명은 자유 텍스트다 (CLAUDE.md: 대학 목록 하드코딩 금지). `User.university`도 자유 텍스트라 일관된다.

### 4.3 게임 보정

상위 스펙 §5.3은 "매칭 확률 +33%"로 표현했으나, 본 설계는 확률이 아닌 점수 체계다. 점수로 환산한다.

| 상황 | 처리 |
|---|---|
| 오작교 — 같은 쌍 지목자 1명 | +33점 |
| 오작교 — 지목자 2명 | +66점 |
| 오작교 — 지목자 3명 이상 | **보장** |
| 붉은실 — 상호 입력 | **보장** |

100점 만점 기준으로 33%씩 얹는 해석이다.

**보장 처리**: 파이프라인 6단계에서 먼저 확정되고 7단계 최적화에서 제외된다.
단 3단계 하드필터를 통과한 페어만 보장된다 — **절대질문이 보장을 이긴다.**

**보장 충돌 해소**: 한 사람이 두 개 이상의 보장에 걸릴 수 있다
(예: A–B 붉은실 상호 + A–C 오작교 3인). 우선순위:

1. 붉은실 상호 > 오작교 3인 (본인이 직접 원한 쪽 우선)
2. 같은 등급끼리 충돌 시 → 궁합 점수 높은 쪽
3. 그래도 동률 → `user_id` 작은 쪽 (재현 가능성)

버려진 쪽은 일반 매칭 풀로 돌아간다.

동성 간 붉은실 상호가 성립한 경우는 무시한다 (남녀 1:1 전제).

### 4.4 게임 대상 유저 식별

붉은실·오작교는 이름+학교 텍스트로만 저장되며 가입 여부를 검증하지 않는다 (상위 스펙 §6).
이를 실제 유저와 연결할 때 동명이인 문제가 발생한다.

**규칙: 이름 + 학교 + 학번으로 유일하게 특정될 때만 게임 효과를 적용한다.**
2명 이상 매치되면 무시한다 (일반 매칭은 정상 진행). 잘못된 사람에게 보장이 붙는 사고를 원천 차단한다.

⚠️ **학번 필드는 아직 없다.** `User.admission_year` 추가 + 회원가입 화면 + 게임 입력 화면 + 기존 유저 백필이
필요하며, 이는 **본 설계 범위 밖의 별도 작업**이다. 학번 도입 전까지는 이름+학교만으로 판정하되
동일 규칙(유일할 때만 적용)을 그대로 쓴다.

## 5. 짝짓기

### 5.1 알고리즘

`scipy.optimize.linear_sum_assignment`(헝가리안)를 사용한다.

남↔여 간선만 존재하는 이분 그래프라 행렬로 표현할 수 있다. 헝가리안은 C 구현이라
순수 Python인 `networkx.max_weight_matching`보다 두세 자릿수 빠르다.

헝가리안은 작은 쪽 전원을 강제로 짝지우므로, 미매칭을 0점 선택지로 넣은
`(남 + 여)` 정사각 패딩 행렬을 쓴다. 미매칭이 항상 0점으로 가능하므로
금지 페어(음수)는 절대 선택되지 않고, 남녀 인원이 달라도 남는 쪽이 자기
미매칭 슬롯으로 흘러간다. 목적함수는 §4·§5.2 그대로다.

**성능** (2026-08-30 실측):

| 풀 규모 | 점수 계산 | 짝 계산 |
|---|---|---|
| 200명 | 0.3s | 0.004s |
| 500명 | 1.9s | 0.034s |
| 1,000명 | ~8s | 0.14s |
| 2,000명 | — | 0.68s |

병목은 이제 짝 계산이 아니라 점수 계산이다 (O(n²)). 2,000명대에서 다시 검토한다.

**한계.** float64는 정수를 2⁵³까지만 정확히 담는다. 가중치가 이를 넘으면 tie 항이
반올림에 먹혀 §5.2의 결정론이 조용히 깨지므로, 넘으면 예외를 던진다. 한계는 풀 크기만으로
정해지지 않는다 — 엔진에 들어가는 값은 raw `pair_score`(최대 100점)가 아니라 이월 보너스·
오작교 보너스까지 더해진 조정 점수(현재 상수 기준 최대 256점)라서, 풀 약 4,100명대가
실제 한계다. `UNIVERSITY_BONUS`가 §12의 미결 상태를 벗어나 0이 아닌 값으로 정해지면 한계는
더 내려간다. 그때는 점수 스케일 축소가 필요하다.

교체 이력과 실측 근거: `2026-08-30-matching-performance-design.md`

### 5.2 결정론성

점수가 같은 조합이 여럿일 때 라이브러리가 임의로 고르면 실행할 때마다 결과가 달라져 테스트가 불안정해진다.
`user_id` 기준 정렬 순번을 tie-break 가중치로 넣어 고정한다.

tie 항은 두 사람의 순번 차이의 제곱이라, 순번이 가까운 사람끼리 묶이는 쪽으로 편향된다.
다만 이 편향이 승부를 유일하게 결정하지는 않는다 — 간선이 빠진 그래프에서 3쌍 이상이면
점수 합과 tie 합이 둘 다 같은 경우가 생길 수 있고, 그때는 scipy 내부 규칙이 남은 동점을 가른다.

**정규화된 페어 키마다 값이 하나뿐인 입력이면, 같은 입력은 항상 같은 결과를 낸다.** `scores`의
키는 `(a, b)`든 `(b, a)`든 상관없이 정규화되는데, 같은 페어를 두 키로 동시에 넘기면 나중 값이
앞 값을 덮어써 결과가 넘긴 순서에 좌우된다 — 실제 호출부(`matching.py`)는 페어당 값을 하나만
넘기므로 이 조건은 항상 충족된다.

순번은 그 라운드 풀 안에서의 등장 순서(0부터)다. id 순서는 보존하되 간격은 무시한다 — raw id
간격을 그대로 쓰면 실제 규모(간격이 큰 sparse id)에서는 tie 항이 `점수 × big`을 통째로 삼켜
모든 실제 페어가 미매칭보다 낮은 점수를 받아 결과가 통째로 빈 매칭이 되고, 풀 자체가 커지면
가중치가 float64의 정확 정수 범위(2⁵³)를 넘는다 — 실제 한계 수치는 §5.1 참고.

### 5.3 성비 불균형

남녀 수가 다르면 많은 쪽에서 남는 인원이 생긴다. 이들은 자동으로 미매칭 처리되어
`missed_rounds`가 1 올라가고 다음 라운드에서 이월 보너스를 받는다. 별도 처리 없음.

### 5.4 재매칭 금지

3단계에서 `matches` 테이블을 조회해 **과거에 한 번이라도 짝이었던 페어는 후보에서 제거**한다.
라운드 수와 무관하게 영구 적용된다.

### 5.5 멱등 실행

관리자 더블클릭·재실행을 방어한다.

```sql
UPDATE match_rounds SET status = 'running'
 WHERE id = ? AND status = 'pending'
```

이 UPDATE가 **0행을 바꾸면** 이미 다른 요청이 선점한 것 → `409 Conflict` 반환 후 종료.
조건부 UPDATE라 검사와 선점이 한 번에 일어나 경쟁 구간이 없다.

`RoundStatus`에 `running` 값을 추가한다 (pending / **running** / done).
실행 중 서버가 죽으면 `running`에 멈춰 있어 관리자가 상황을 인지할 수 있다.

SQLite가 `SELECT FOR UPDATE`를 지원하지 않고 현재 개발 DB가 SQLite이므로 이 방식을 택했다.
조건부 UPDATE는 SQLite·PostgreSQL 양쪽에서 원자적으로 동작한다
(커밋 `b41c173`의 라운드 중복 방지와 같은 접근).

### 6.1 변경

| 대상 | 변경 |
|---|---|
| `User` | `missed_rounds` (int, 기본 0) 추가 |
| `RoundStatus` | `running` 값 추가 |

`Match.score`를 기록하는 이유: 카테고리 가중치를 나중에 조정하려면 "지금 매칭들이 몇 점짜리였나"

저장 시 `user_a` = 남성, `user_b` = 여성으로 고정한다.
두 제약이 실제로 목적을 달성하려면 축이 사람이 아니라 성별에 묶여야 한다 —
id 대소로 정규화하면 같은 사람이 라운드 안에서 `user_a`와 `user_b`를 넘나들어 제약을 빠져나간다.

### 7.1 `GET /me/match` 정의

**가장 최근에 `done` 상태가 된 라운드**(= `executed_at`이 가장 늦은 라운드)에서 내가 포함된 `Match` 행을 반환한다.

| 상황 | 응답 |
|---|---|
| 매칭됨 | 상대 `name`, `university`, 연락처(`instagram` / `kakao_id` / `phone` 중 입력된 것), 라운드 `executed_at` |
| 그 라운드에서 미매칭 | `null` |
| 아직 실행된 라운드가 없음 | `null` |

지난 라운드 이력은 반환하지 않는다 — 인앱 화면은 "이번 주 결과"만 보여준다.
`score`는 내부 운영용이므로 유저에게 노출하지 않는다.

## 10. 작업 분할

4단계로 나눈다. 각 단계는 끝났을 때 그 자체로 동작하는 상태가 된다.

| 단계 | 내용 | 선행 이유 |
|---|---|---|
| **1. 카탈로그 이전** | `questions.ts` → `catalog.py` + `GET /survey/questions` + 프론트 설문 화면 리팩터 | 점수 계산의 전제. 없으면 2단계 착수 불가 |
| **2. 매칭 엔진** | scoring · pairing · matching + 실행 API + 관리자 실행 버튼 | 핵심. 대학 가중치는 상수 0으로 자리만 마련 |
| **3. 대학 가중치** | 테이블 + CRUD API + 관리자 탭 | 2단계 없이는 붙일 데가 없음 |
| **4. 인앱 결과 화면** | `GET /me/match` + 홈 카드 | 매칭 결과가 나와야 만들 수 있음 |

**본 설계 범위 밖** (별도 작업):
- 학번 필드 추가 (§4.4) — 회원가입·User 모델·게임 화면·기존 유저 백필
- 카카오 알림톡 — 사업자등록 완료 후
- 스케줄러 자동 실행 — 배포 환경 구축 후
