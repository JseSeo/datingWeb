# 가입 데이터 정합성 설계 — 대학 목록 · 연락처 · 학번

- 작성일: 2026-09-04
- 선행 스펙: `2026-08-21-matching-algorithm-design.md` (§4.4 · §6.2 · §12)
- 상태: 설계 확정, 미구현

---

## 1. 개요

유저가 입력한 **대학명 · 연락처 · 학번**이 매칭 결과의 정확도를 직접 좌우하는데,
지금은 셋 다 강제되지 않는다. 그 결과 매칭이 *에러 없이 조용히 틀린다*.

세 가지를 한 작업으로 묶는다. 셋 다 회원가입 · `User` 모델 · 마이그레이션이라는
같은 면을 건드리고, 대학 목록과 학번은 **둘 다 게임 지목 테이블을 고치기** 때문이다.
따로 하면 같은 테이블에 마이그레이션을 두 번 얹는다.

**목표**

| # | 목표 |
|---|---|
| 1 | 대학명을 사람이 타이핑하는 경로를 전부 없앤다 — 관리자가 관리하는 목록에서 고른다 |
| 2 | 연락처 없는 유저가 매칭되지 않게 한다 |
| 3 | 동명이인 때문에 게임 지목이 사라지는 것을 학번으로 줄인다 (선택 입력, 정확도 한계는 명시) |

## 2. 배경 — 지금 무엇이 깨져 있나

### 2.1 대학명

대학명을 사람이 타이핑하는 곳이 4군데다.

| 화면 | 누가 입력 | 저장 위치 |
|---|---|---|
| 회원가입 | 유저 본인 학교 | `users.university` |
| 오작교 지목 | 유저가 **남의** 학교 2명분 | `ojakgyo.person_a/b_university` |
| 붉은실 지목 | 유저가 **남의** 학교 | `red_threads.target_university` |
| 관리자 가중치 규칙 | 관리자 | `matching_university_weights.university_a/b` |

전부 자유 텍스트고 전부 문자열로 그대로 비교된다. 표기가 한 글자만 달라도:

- **대학 가중치 규칙이 조용히 안 먹는다** (선행 스펙 §12에 기록된 항목)
- **게임 지목이 조용히 사라진다.** 가입자는 "연세대학교"로 저장됐는데 지목자가 "연세대"라고
  치면 `_identity_resolver`가 후보를 못 찾는다. 에러도 로그도 없다.

두 번째가 더 심각하다. 학번을 넣는 것도 결국 이 함수의 정확도를 올리자는 얘기라,
**학교 표기부터 통일되지 않으면 학번은 소용이 없다.**

실제로 개발 DB의 테스트 유저 4명이 이미 4가지 표기로 갈려 있다.

### 2.2 연락처

`instagram` · `kakao_id` · `phone` 셋 다 nullable이고, 회원가입 폼에는 **필드 자체가 없다**
(가입 후 마이페이지에서 입력). 연락처가 0개인 유저도 매칭 자격을 통과하므로,
매칭돼도 서로 연락할 방법이 없다 — 결과가 무의미해진다.

### 2.3 학번

`User.admission_year`가 없다. `_identity_resolver`는 이름+학교로만 판정하고,
후보가 2명 이상이면 무시한다. 안전한 실패지만 동명이인의 지목은 전부 버려진다.

## 3. 접근 — 문자열 저장 + 쓰기 경로 검증

**고른 대학의 이름(문자열)을 지금처럼 각 테이블에 저장하고, 값이 들어오는 모든 쓰기
경로에서 목록 대조 검증을 건다.** 컬럼 타입은 바뀌지 않는다.

### 3.1 왜 FK 정규화가 아닌가

`universities.id`를 참조하는 정규화가 무결성 면에서는 낫다. 채택하지 않은 이유는 하나다.

`matching_university_weights`의 **단일 대학 규칙이 `university_b = ''`(빈 문자열) 관례**를
쓴다. FK 정수로 바꾸면 빈 문자열을 못 쓰고 NULL을 써야 하는데, 이 테이블은
**NULL을 피하려고 일부러 NOT NULL로 만들어졌다** — nullable이면 유니크 인덱스가 NULL을
서로 다른 값으로 봐서 중복 규칙이 조용히 합산되기 때문이다 (2026-09-03 PR #25).
FK로 가려면 센티넬 행이나 별도 `kind` 컬럼을 새로 도입해야 하고, 하루 전에 고친 버그를
다시 열 위험이 있다.

출시 전이라 FK의 무결성 이점은 아직 실익이 없는 반면 위험은 실재한다.
쓰기 경로가 4개뿐이라 검증 누락 위험도 관리 가능한 크기다.

### 3.2 이 접근의 약점과 방어

DB 레벨 참조 무결성이 없다. 검증을 빠뜨린 쓰기 경로가 새로 생기면 구멍이 뚫린다.

방어: **검증을 함수 하나로 모으고**(§5.1), **경로마다 테스트를 건다**(§12).

## 4. 데이터 모델

### 4.1 신설 `universities`

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | Integer PK | |
| `name` | String(100) UNIQUE NOT NULL | 표준 표기. 이것이 유일한 진실 |
| `active` | Boolean NOT NULL default true | |
| `created_at` | DateTime NOT NULL | |

**이름 변경(rename) 기능은 만들지 않는다.** 이 설계는 대학명 문자열을 각 테이블에 복사해
저장하므로, 목록에서 이름을 고치면 이미 저장된 유저 · 지목 · 가중치 행이 전부 고아가 된다.
지금 고치려는 그 버그가 그대로 재발한다.

CRUD는 **추가 / 활성 토글 / 삭제**만 — `matching_university_weights` 관리 화면과 같은 패턴.

**삭제는 참조가 0건일 때만.** 참조가 있으면 409를 반환하고 "비활성으로 끄세요"를 안내한다.
참조 검사 대상: `users` · `ojakgyo` · `red_threads` · `matching_university_weights`.

### 4.2 학번 컬럼

학번은 **입학년도 4자리**다 (`admission_year`).

| 테이블 | 컬럼 | NULL 정책 |
|---|---|---|
| `users` | `admission_year` | **nullable** — 미입력은 NULL |
| `ojakgyo` | `person_a_admission_year`, `person_b_admission_year` | **NOT NULL, server_default 0** (0 = 미입력) |
| `red_threads` | `target_admission_year` | **NOT NULL, server_default 0** |

표현이 갈리는 데는 이유가 있다.

지목 테이블은 학번을 **유니크 제약에 넣어야 한다.** 안 넣으면 동명이인 두 명을 각각
지목하는 것이 중복으로 막히고, 넣으면 구분해서 지목할 수 있다. 그런데 NULL을 유니크 키에
넣으면 DB가 NULL끼리 서로 다르다고 보아 **같은 사람을 학번 없이 몇 번이고 중복 지목**할 수
있게 된다 — §3.1의 `university_b`와 정확히 같은 함정이다. 그래서 지목 쪽만 0 센티넬을 쓴다.

`users.admission_year`는 유니크 키에 들어가지 않고 API 응답에 그대로 나가므로 NULL이 정직하다.

유니크 제약 변경:

| 제약 | 변경 후 |
|---|---|
| `uq_ojakgyo_recommender_pair` | `(recommender_id, person_a_name, person_a_university, person_a_admission_year, person_b_name, person_b_university, person_b_admission_year)` |
| `uq_red_thread_user_target` | `(user_id, target_name, target_university, target_admission_year)` |

**값 범위**: 입력받는 학번은 `2000 ≤ admission_year ≤ 현재 연도 + 1`만 허용하고, 벗어나면 422.
상한을 현재 연도가 아니라 +1로 두는 이유는 신입생이 입학 전 학기에 가입할 수 있기 때문이다.
지목 테이블의 `0`은 미입력 센티넬이므로 이 범위 검증의 예외다 — 스키마 기본값일 뿐,
API로 `0`을 직접 받지는 않는다(미입력은 필드를 비워 보낸다).

### 4.3 마이그레이션

리비전 **1개**:

1. `universities` 생성
2. 학번 컬럼 4개 추가
3. 지목 테이블 2개의 유니크 제약 재생성 (SQLite이므로 `batch_alter_table`)

연락처는 **스키마 변경 없음** — 이미 nullable 3개가 있고 검증만 붙는다.

**마이그레이션은 기존 행을 검사하지 않는다.** 이 설계의 검증은 DB 제약이 아니라 애플리케이션
레벨이므로, 목록에 없는 대학명을 가진 기존 행이 있어도 통과한다. 개발 DB의 테스트 유저 4명이
정확히 그 상태다 — 운영 전 수동 정리 대상이며 §13에 기록한다.

## 5. 검증

### 5.1 공용 모듈 `app/services/universities.py`

| 이름 | 역할 |
|---|---|
| `known_names(db)` | 활성 대학명 집합 반환 |
| `UnknownUniversity` | 도메인 예외 — 목록에 없는 이름이 들어왔을 때 |
| `require_known(db, *names)` | 모르는 이름이 있으면 `UnknownUniversity` raise |

서비스는 HTTP를 모른다 (선행 스펙 §2.1). API 계층에서 예외를 잡아 **422**로 바꾼다.

### 5.2 검증을 거는 쓰기 경로

| 경로 | 검증 대상 |
|---|---|
| `POST /auth/register` | `university` |
| `POST /game/ojakgyo` | `person_a_university`, `person_b_university` |
| `POST /game/red-thread` | `targets[].target_university` |
| `POST /admin/university-weights` | `university_a`, `university_b` — **`university_b = ''`는 건너뛴다** (단일 대학 규칙 관례) |

### 5.3 활성 / 비활성 정책

**신규 쓰기는 활성 대학만 허용한다.** 비활성으로 끈 대학은 새로 고를 수 없지만, 이미 그
대학으로 가입한 유저는 그대로 유지되고 매칭도 계속된다. 삭제가 아니라 비활성인 이유가 이것이다.

## 6. 게임 지목 대상 특정 (`_identity_resolver`)

선행 스펙 §4.4의 "이름 + 학교 + 학번으로 유일하게 특정될 때만 적용" 규칙을 실제로 구현한다.

### 6.1 알고리즘

```
후보 = index[(이름, 학교)]

if 지목자가_적은_학번:
    일치 = [h for h in 후보 if h.학번 == 지목자가_적은_학번]
    if len(일치) == 1:
        return 일치[0]          # 동명이인 해결
    # 0명이거나 2명 이상이면 학번으로 못 좁힘 → 아래로 폴백

return 후보[0] if len(후보) == 1 else None
```

학번은 **후보를 좁히는 추가 필터**로만 쓴다. 학번 미등록 유저를 후보에서 배제하지 않는다.

### 6.2 동작

| 후보 수 | 지목자 학번 | 결과 |
|---|---|---|
| 1명 | 없음 | 특정 (기존 동작 유지) |
| 2명 이상 | 있고 1명만 일치 | **특정** — 학번의 목적 |
| 2명 이상 | 없음 / 안 좁혀짐 | 무시 (None) |
| 2명 이상 | 학번까지 같은 동명이인 | 무시 (None) |
| 1명 | 있는데 불일치 | **특정** (폴백, §6.3) |

### 6.3 폴백 판단

후보가 1명인데 지목자가 학번을 다르게 적은 경우 — 대상이 학번을 등록하지 않았거나(대조 불가),
지목자가 잘못 안 것이다. 이때 무시하면 **학번을 안 적었으면 성공했을 지목이, 학번을 적었다는
이유로 실패**하는 이상한 동작이 된다. 그래서 폴백해서 특정한다.
이름과 학교가 맞고 그 학교에 그 이름이 한 명뿐이면 그 사람으로 본다.

### 6.4 정확도 안내 문구

학번은 선택 입력이다 — 상대의 학번을 모를 수 있기 때문. 대신 정확도 한계를 화면에 명시한다.

| 화면 | 문구 |
|---|---|
| 게임 지목 폼 | "선택 입력. 동명이인이 있으면 학번 없이는 지목이 반영되지 않을 수 있습니다." |
| 회원가입 폼 | "선택 입력. 입력하지 않으면 다른 사람이 회원님을 지목할 때 동명이인과 구분되지 않을 수 있습니다." |

## 7. 연락처

### 7.1 3중 방어

| 지점 | 처리 |
|---|---|
| 가입 | `RegisterRequest`에 `instagram` · `kakao_id` · `phone` 추가(각각 선택) + **최소 1개** 검증 → 422. 빈 문자열은 None으로 정규화 (`ProfileUpdate`와 같은 패턴) |
| 프로필 수정 | `PUT /me/profile`는 `exclude_unset=True` 부분 업데이트다. payload가 아니라 **병합 결과**로 판정한다. 적용 후 3개가 모두 비면 422 — `setattr` 전에 계산해 DB에 닿지 않게 한다 |
| 매칭 자격 | `eligible_users`에 "연락처 1개 이상" 조건 추가 |

전화번호 형식 검증은 하지 않는다 (요청 범위 밖, YAGNI).

### 7.2 선행 스펙 §6.2 변경

| 조건 | 비고 |
|---|---|
| `status = active` | 학생증 승인 완료 |
| `matching_paused = false` | 마이페이지 일시정지 OFF |
| Survey 행 존재 | 응답 개수는 따지지 않음 (부분 응답 허용) |
| **연락처 1개 이상** | `instagram` · `kakao_id` · `phone` 중 최소 1개 (신규) |

## 8. API

| 메서드 | 경로 | 인증 | 설명 |
|---|---|---|---|
| GET | `/universities` | **없음** | 활성 대학 목록. 가입 폼이 로그인 전에 호출한다 |
| GET | `/admin/universities` | 관리자 | 비활성 포함 전체 |
| POST | `/admin/universities` | 관리자 | 추가. 중복 이름 409 |
| PATCH | `/admin/universities/{id}` | 관리자 | `active` 토글만. 이름 변경 없음 (§4.1) |
| DELETE | `/admin/universities/{id}` | 관리자 | 참조 0건일 때만. 아니면 409 |

기존 엔드포인트 변경: `POST /auth/register` (대학 검증 + 학번 + 연락처),
`POST /game/ojakgyo` · `POST /game/red-thread` (대학 검증 + 학번),
`PUT /me/profile` (연락처 최소 1개), `POST /admin/university-weights` (대학 검증).

## 9. 화면

| 화면 | 변경 |
|---|---|
| Register | 학교 셀렉트 + 학번(선택) + 연락처 3개 및 최소 1개 안내 |
| Game / OjakgyoTab | 학교 셀렉트 ×2, 학번(선택) ×2 + 안내 문구 |
| Game / RedThreadTab | 학교 셀렉트, 학번(선택) + 안내 문구 |
| Admin / UniversityWeightTab | 대학명 2개를 셀렉트로. 두 번째 "없음" = 단일 대학 규칙 (`university_b = ''`) |
| Admin / **UniversityTab** (신규) | 5번째 탭. 추가 · 활성 토글 · 삭제 |
| MyPage | 마지막 연락처 삭제 시 에러 표시 |

셀렉트가 4곳에 나오므로 공용 컴포넌트 `components/UniversitySelect` 하나로 만든다.

**목록이 비어 있으면 가입이 막힌다.** 관리자가 대학을 하나도 등록하지 않으면 셀렉트가 빈 채로
뜨고 가입을 진행할 수 없다. 이는 의도된 동작이다 — 자유 텍스트로 돌아가는 우회로를 두면 이
작업 전체가 무의미해진다. 팀이 대학 목록을 채우기 전까지는 가입이 불가능하다.

## 11. 작업 분할

3단계. 각 단계는 끝난 시점에 그 자체로 동작한다.

| 단계 | 내용 | 선행 이유 |
|---|---|---|
| **1. 대학 목록 기반** | `universities` 테이블 + CRUD + 관리자 탭 + `GET /universities` + `require_known` + 쓰기 4경로 검증 + 셀렉트 4곳 | 학번·연락처가 붙을 가입 폼을 먼저 정리한다. 이 단계만으로 §2.1이 닫힌다 |
| **2. 연락처 필수** | 가입 폼 3필드 + 최소 1개 검증 3중 + `eligible_users` 조건 | 1단계와 독립이지만 같은 가입 폼을 고치므로 이어서 한다 |
| **3. 학번** | 학번 컬럼 4개 + 유니크 제약 재생성 + `_identity_resolver` + 입력 화면 3곳 + 안내 문구 | 대학 표기가 통일된 뒤에야 의미가 있다 (§2.1) |

마이그레이션은 §4.3대로 **1개 리비전**에 몰아 넣고 1단계에서 적용한다 — 지목 테이블을 두 번
고치지 않기 위해서다. 2·3단계는 스키마 변경 없이 코드만 얹는다.

## 12. 테스트 전략

TDD로 진행한다 (CLAUDE.md: `test-driven-development` 우선).

| 대상 | 케이스 |
|---|---|
| `require_known` | 활성 통과 / 비활성 거부 / 없는 이름 거부 / `''` 예외(가중치 단일 규칙) |
| 쓰기 4경로 | 각각 목록 밖 이름 → 422 |
| `GET /universities` | 비인증 접근 가능, 비활성 제외 |
| 대학 삭제 | 참조 있으면 409, 없으면 204. 참조 4종 각각 |
| `_identity_resolver` | §6.2 표 5행 전부 |
| 학번 범위 | 1999·미래 연도 → 422 / 현재 연도 + 1 → 통과 (§4.2) |
| 연락처 | 가입 0개 → 422 / 프로필 마지막 1개 삭제 → 422 / 2개 중 1개 삭제 → 성공 |
| `eligible_users` | 연락처 0개 유저는 풀에서 제외 |
| 마이그레이션 | 임시 sqlite에 upgrade → downgrade 실측 + `compare_metadata`로 모델↔마이그레이션 드리프트 0 |

마이그레이션 테스트가 따로 필요한 이유: 테스트 스위트는 `Base.metadata.create_all`로 스키마를
만들어 **마이그레이션을 타지 않는다.** PR #25에서 쓴 방식을 그대로 따른다.

## 13. 미결 / 운영 전 확인

| 항목 | 상태 |
|---|---|
| 16개 대학 목록의 실제 값 | 팀 결정 필요. **목록이 비면 가입 불가**(§9) — 출시 전 필수 입력 |
| 개발 DB 기존 유저 4명 | 대학명이 목록 밖, 연락처 0개. 마이그레이션이 검사하지 않으므로(§4.3) 수동 정리 필요 |
| 학번 미입력 시 정확도 하락 | 안내 문구로 명시(§6.4). 미입력 비율이 높으면 필수 전환 재검토 |
| 대학 이름 변경 요구 | 기능을 만들지 않았다(§4.1). 실제로 필요해지면 참조 행 일괄 갱신을 포함한 별도 설계 필요 |
| 캠퍼스 구분 | "○○대학교 △△캠퍼스"를 별도 항목으로 둘지 팀 결정. 현재 설계는 목록에 넣기만 하면 동작한다 |
