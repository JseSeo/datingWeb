# 신고 & 건의 — 설계안 (design doc)

**작성: 2026-08-02 · 상태: 🟡 검토 요망 (brainstorming 산출물)**

---

## 1. 목표 · 범위

프론트 `/report` 페이지 구축. 유저가 **부적절 유저 신고** 또는 **서비스 건의**를 제출하는 화면 하나. 유형은 폼 안의 라디오로 구분.

**현재 상태 (착수 전):**

| 층 | 상태 |
|---|---|
| DB 모델 | `models/report.py` — `reporter_id`, `target_id`(FK, 필수), `reason` |
| API | `POST /reports` (`api/reports.py`) |
| 프론트 api 함수 | 없음 |
| 페이지 · 라우트 | 없음 |

**해결해야 할 모순:** 스펙(`2026-05-23-datedrop-korea-design.md:106`)은 화면을 "신고 & 건의"로 정의하지만, 모델·API는 신고만 표현 가능. `target_id`가 `nullable=False`라 대상 없는 건의를 저장할 수 없음. 또한 프론트가 다른 유저의 `target_id`를 알아낼 API가 없어 신고 화면 자체를 만들 수 없음.

**이 설계가 만드는 변경:**
1. `Report` 모델 — `target_id` FK 제거, `target_name`/`target_university` 텍스트 + `type` 추가 (+ 마이그레이션)
2. `POST /reports` 요청 스키마 · 검증 규칙 개편
3. 프론트 `/report` 페이지 + 라우트 + `lib/api.ts` 함수 + MyPage 진입 행

**범위 밖:**
- ⛔ **매칭 알고리즘** — 금지 항목. 이 설계는 매칭에 의존하지 않음
- 관리자 신고 조회 (§7)
- 대상 자동완성 (§7)

## 2. 확정 결정 요약

| # | 질문 | 결정 |
|---|------|------|
| Q1 | 신고 대상을 어떻게 특정? | **이름 + 학교 텍스트 입력.** 오작교·붉은실과 동일 패턴. `target_id` FK 폐기 |
| Q2 | 신고와 건의를 같은 테이블에? | **같은 테이블 + `type` 컬럼.** 건의는 대상 필드 null |

| Q4 | 실존 확인을 자동완성으로? | **아니오.** 개인정보 노출 위험 (§6). 대신 본문 안내문으로 식별 단서 유도 |

## 3. 데이터 모델

```
Report
  id                 Integer PK
  reporter_id        FK users.id, 필수
  type               Enum("report", "suggestion"), 필수      ← 신규
  target_name        String(100), nullable                   ← 신규
  target_university  String(100), nullable                   ← 신규
  reason             Text, 필수
  created_at         DateTime, 필수
```

**변경 요약:** `target_id` 삭제. `target_name`·`target_university`·`type` 추가.

`target_name`/`target_university`가 nullable인 이유는 건의에 대상이 없기 때문. "신고면 반드시 채워짐"은 **DB 제약이 아니라 API 검증**으로 강제한다 — DB에서 조건부 필수를 표현하려면 CHECK 제약이 필요한데, 규칙이 한 곳(API)에만 있는 편이 읽기 쉽다.

컬럼명 `target_name`·`target_university`와 타입 `String(100)`은 붉은실(`models/game.py:44-45`)과 정확히 동일하다. 새 이름·타입을 만들지 않는다.

이름·학교는 **strip 후 저장**. 오작교·붉은실 규칙과 동일(`CLAUDE.md` 도메인 규칙).

**마이그레이션:** 새 alembic revision 1개. `type`이 필수 컬럼이라 기존 행이 있으면 채울 값이 필요하다. 착수 시 `reports` 테이블이 비었는지 먼저 확인한다. 비어 있으면 `server_default` 없이 추가한다 — `User.gender`에서 `server_default="male"` 때문에 생긴 백필 숙제를 반복하지 않기 위함. 행이 있으면 사용자에게 처리 방침을 다시 묻는다.

## 4. API 계약

`POST /reports` 하나 유지. 인증은 `get_current_user` 그대로 (인증 대기 유저도 제출 가능 — 기존 동작 유지).

**요청 `ReportCreate`**

| 필드 | 타입 | 규칙 |
|---|---|---|
| `type` | `"report"` \| `"suggestion"` | 필수 |
| `target_name` | str \| null | 신고면 필수, 건의면 무시. max_length 100 |
| `target_university` | str \| null | 신고면 필수, 건의면 무시. max_length 100 |
| `reason` | str | 필수. strip 후 빈 값 거부. max_length 2000 |

`max_length=100`은 오작교 필드와 맞춘 값(커밋 `5ba968c`). 새 기준을 만들지 않는다.

**검증 순서 (모두 400)**

1. `reason` strip 후 빈 값 → `"내용을 입력하세요"`
2. `type=report`인데 `target_name` 또는 `target_university`가 빈 값 → `"신고 대상의 이름과 학교를 입력하세요"`
3. `type=report`이고 대상 이름·학교가 본인과 일치(strip 후 비교) → `"자기 자신을 신고할 수 없습니다"`

3번은 기존 `reports.py:19`의 자기신고 차단을 이름+학교 비교로 옮긴 것. 오작교의 "본인은 두 사람에 못 들어감" 규칙과 같은 성격.

**저장 규칙**

- `type=suggestion` → `target_name`·`target_university`를 **강제로 null**. 클라이언트가 무엇을 보내든 무시한다.
- 이름·학교는 strip 후 저장.

**사라지는 검증**

기존 `reports.py:24-29`의 404 `"존재하지 않는 사용자입니다"`는 제거된다. 대상이 텍스트라 실존 여부를 확인할 수단이 없다. 오타나 없는 사람을 적어도 접수되며, 관리자가 판단한다. §6의 트레이드오프가 코드로 드러나는 지점.

**응답 `ReportOut`**: `id`, `type`, `target_name`, `target_university`, `reason`, `created_at`

## 5. 프론트엔드

**라우트:** `/report`. `MainLayout` **바깥**(하단 탭이 아닌 하위 화면 — `/profile`과 동일 취급). `<ProtectedRoute>`만 적용하고 `requireStatus`는 두지 않는다. 백엔드가 `get_current_user`인 것과 맞춘다.

**진입 경로:** MyPage 하단 카드에 행 추가.

```
로그아웃          ›
신고 & 건의       ›     ← 추가
회원 탈퇴         ›
```

**폼 구성 (`pages/Report/Report.tsx`)**

| 요소 | 동작 |
|---|---|
| 유형 라디오 | 신고 / 건의. **기본 미선택** → 제출 버튼 비활성. Register의 성별 처리(`Register.tsx:113`)와 동일 패턴 |
| 이름 · 학교 입력 | `type=report`일 때만 렌더. 건의 선택 시 화면에서 사라짐 |
| 안내문 | 신고일 때만: "학과·학번·인스타 아이디 등 대상을 특정할 수 있는 정보를 본문에 함께 적어주세요" |
| 본문 textarea | 항상 표시. 유형에 따라 placeholder만 변경 |
| 제출 버튼 | 유형 미선택 또는 전송 중이면 비활성 |

이름·학교를 비활성화가 아니라 **렌더 자체를 끊는** 이유: 입력칸이 사라지면 "채울 필요 없음"이 화면으로 드러난다. 회색 칸이 남으면 오히려 헷갈린다.

**제출 결과:** Survey의 상태 패턴(`Survey.tsx:20`)을 재사용 — `"" | "sending" | "sent" | "error"`. 성공 시 "접수되었습니다" 표시 후 폼 초기화. 화면 이동은 하지 않는다(연달아 작성 가능).

**에러 처리:** `lib/api.ts`의 `ApiError`가 서버 detail을 전달한다(`Register.tsx:55` 패턴). 백엔드 400 문구를 그대로 노출하고, 프론트에서 문구를 다시 만들지 않는다. 메시지의 진실원은 백엔드 하나.

**재사용:** `Input`, `Button` 기존 컴포넌트. `lib/api.ts`에 `submitReport()` 추가.

## 6. 자동완성을 채택하지 않은 이유

검토안: 이름·학교 입력 시 일치하는 회원의 아이디 앞 3글자를 자동완성으로 보여준다.

**기각.** 회원 조회 API를 만든다는 뜻이고, 신고 화면은 로그인만 하면 누구나 접근한다.

1. **가입자 열람** — 이름 몇 글자로 훑으면 특정 대학에 누가 가입했는지 목록을 뽑을 수 있다. 소개팅 서비스에서 지인·전 연인 탐색은 가장 흔한 악용 유형이다.
2. **아이디 부분 노출** — 앞 3글자라도 로그인 식별자다. 이름·학교와 함께 노출되면 피싱·비밀번호 추측의 재료가 된다.
3. **법적 문제** — 이용자 정보를 다른 이용자에게 보여주는 것은 개인정보 제3자 제공이다. 현재 가입 동의 항목은 이용약관·개인정보처리방침·만14세 셋뿐(`Register.tsx:18-20`)이라 근거가 없다.

"존재 여부만 true/false로 반환" 역시 기각한다. 이름을 바꿔가며 반복 호출하면 결국 명부가 재구성된다.

**대신:** 자유 입력을 유지하고(§4), 본문에 식별 단서를 적도록 안내문으로 유도한다(§5). 새 API 없이 관리자 식별력을 높인다.

**트레이드오프 (감수하는 손실):** 대상 특정 정확도. 동명이인이나 오타를 시스템이 걸러내지 못하며, 관리자가 수동 판단해야 한다. 이는 오작교·붉은실이 이미 감수하고 있는 것과 동일한 수준이다.

## 8. 테스트 계획

프로젝트 규칙상 **TDD** — 구현 전 작성.

**백엔드 (`pytest`)**

| # | 케이스 | 기대 |
|---|--------|------|
| 1 | 신고 + 이름·학교 정상 | 201, 저장값 strip됨 |
| 2 | 신고인데 이름 또는 학교 누락 | 400 `"신고 대상의 이름과 학교를 입력하세요"` |
| 3 | 건의 + 이름·학교를 보냄 | 201, 저장된 이름·학교 **null** |
| 4 | 본문이 공백뿐 | 400 `"내용을 입력하세요"` |
| 5 | 대상이 본인 이름·학교와 일치 | 400 `"자기 자신을 신고할 수 없습니다"` |
| 6 | 토큰 없음 | 401 |

3번·5번이 이 설계의 핵심 규칙이므로 반드시 고정한다.

**프론트 (`vitest`)**

| # | 케이스 |
|---|--------|
| 1 | 초기 유형 미선택 → 제출 버튼 비활성 |
| 2 | 신고 선택 → 이름·학교 입력 + 안내문 노출 |
| 3 | 건의 선택 → 이름·학교 입력 사라짐 |
| 4 | 제출 성공 → "접수되었습니다" + 폼 초기화 |
| 5 | 서버 400 → 에러 메시지 표시 |
| 6 | MyPage "신고 & 건의" 클릭 → `/report` 이동 |
